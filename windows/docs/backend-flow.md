# Auto-Launch multi-agent — Windows

## Investigasi Auto-Quit setelah Tahap 4

Pada run Windows 9 Oktober 2026, `settings.json` berisi Auto-Quit ON dan `autoQuitDelayMinutes=5`. Proses Coucou berjalan dari `target\release\coucou.exe` mulai 18:08:08, setelah file binary itu ditulis pukul 18:05:08. `coucou.log` mencatat startup 18:08:09 dan hanya satu event sesi sebelum sesi baru berikutnya: `SessionEnd` pukul 18:18:52. Tidak ada `SessionStart` atau `UserPromptSubmit` setelah startup sampai `SessionEnd` tersebut. Tracker sengaja mengabaikan `SessionEnd` yang tidak memiliki sesi terdaftar, sehingga tidak ada countdown yang dapat dimulai pada run ini. Penyebab event awal tidak tertangkap belum terbukti; sesi mungkin sudah berjalan sebelum Coucou restart. Menganggap `SessionEnd` yatim sebagai bukti semua sesi selesai akan membahayakan sesi lain, sehingga aturan ini tidak diubah.

Diagnostik baru menulis baris `auto_quit` ke `%LOCALAPPDATA%\Coucou\coucou.log`: pengaturan ON/durasi, jumlah sesi aktif per kategori agent, ketidakpastian, sisa deadline, hasil `SessionEnd` seperti `orphan_end`/`accepted_end`, pengiriman check, dan alasan check tertahan (`settings_open`, `chat_history`, `permission_pending`, `window_focused`, dan lainnya). Tidak ada session ID, prompt, jawaban, token, API key, atau isi Chat. Log lama tidak memuat alasan tersebut, jadi ia tidak dapat membuktikan status guard pada run sebelumnya.

Tes deterministik Rust memakai waktu `Instant` simulasi untuk 5 dan 60 menit tanpa menunggu. Build debug khusus E2E memakai `COUCOU_AUTO_QUIT_TEST=1` untuk perintah injeksi event terbatas dan offset jam logis; build release tidak mendaftarkan perintah test tersebut. `e2e/run.ps1` menolak berjalan ketika Coucou lain aktif, memakai APPDATA/LOCALAPPDATA terisolasi, lalu menjalankan WebdriverIO + `@wdio/tauri-service` dengan driver resmi Windows. Skenario memeriksa Settings, persistensi, `SessionEnd` yatim, sesi aktif, pembatalan countdown oleh sesi baru, multi-agent, deadline, Settings guard, proses berhenti, dan satu Auto-Launch setelah Quit. Dependensi WDIO belum terpasang di sandbox ini: npm offline tidak memiliki cache dan akses registry ditolak (`ECONNREFUSED`); jalankan `rtk npm run test:e2e` di PowerShell Windows dengan internet. Native GUI E2E belum dapat diklaim lulus di sini.

## Tahap 4: durasi Auto-Quit

`autoQuitDelayMinutes` disimpan di `settings.json` bersama `autoQuitWhenAgentsFinish`. Properti yang tidak ada atau tidak valid memakai 10; nilai yang diterima hanya 5, 10, 15, 30, dan 60. Waktu awal ketika semua sesi terverifikasi berakhir dipertahankan saat durasi berubah, sehingga deadline baru dihitung dari waktu itu. Timer lama dibatalkan sebelum pengganti dibuat; revisi dan ticket membatalkan pemeriksaan lama. Jika durasi baru sudah lewat, pemeriksaan tetap tunduk pada perlindungan Settings, Chat, permission, fokus, dan interaksi pengguna. Deteksi akhir sesi, hooks, plugin, relay, dan Auto-Launch tidak berubah.

Pemeriksaan Tahap 4: `tsc --noEmit`, `cargo check --workspace --offline`, `cargo fmt --check`, serta 23 file tes frontend yang dijalankan satu per satu lulus; satu tes layout berbasis Edge dilewati karena sandbox menolak proses browser. Rust workspace lulus 230 tes app dan 54 tes hook, termasuk tes proses Auto-Launch; tes relay ON yang memakai named pipe dilewati karena pipe dipakai atau akses ditolak. Run Rust awal tanpa direktori data khusus gagal pada satu tes file karena `Access is denied`; run ulang dengan APPDATA/LOCALAPPDATA sementara di `target` lulus. `npm test` bawaan dan Vite build tidak bisa membuka proses anak (`spawn EPERM`), sementara TypeScript lulus. Timing GUI Windows Tahap 4 belum diuji manual.

## Tahap 3A: preview Antigravity

[Kontrak hooks Antigravity](https://www.antigravity.google/docs/hooks/) menyediakan `conversationId`, `transcriptPath`, `invocationNum`/`initialNumSteps` pada invocation, lalu `executionNum`/`fullyIdle` pada Stop; Stop tidak menyediakan teks respons. Pemeriksaan read-only transcript lokal kedua aplikasi menemukan baris `USER_EXPLICIT/USER_INPUT` dan `MODEL/PLANNER_RESPONSE`, tetapi baris tersebut tidak memiliki ID invocation/execution. Dokumentasi tidak menjamin bahwa baris model terakhir pada waktu Stop adalah jawaban final giliran itu; ia bisa berupa pesan antara, teks dari giliran sebelumnya, atau belum tertulis. Parser transcript berisiko salah atribusi dan membaca isi percakapan. Karena itu kode monitoring tetap memakai `Session finished` bila hook tidak memberikan jawaban tepercaya. Tes dengan metadata kedua runtime membuktikan prompt, output tool, dan path transcript tidak dijadikan respons. Tidak ada transcript yang disalin, diubah, atau dikirim keluar.

## Tahap 3B: Auto-Quit

`autoQuitWhenAgentsFinish` disimpan sebagai preferensi terpisah, default OFF. Backend `auto_quit.rs` melacak `(agent, session_id)` dari relay, tidak memakai pill/fokus/idle/Stop sebagai bukti akhir sesi. Relay baru memberi cap waktu mikrodetik tanpa isi prompt; event tanpa cap waktu dari binary lama membuat sesi tidak memenuhi syarat quit. SessionEnd yang belum mempunyai sesi, duplikat, atau lebih tua dari aktivitas terakhir tidak mengakhiri sesi. Identitas yang digunakan ulang dan status tak pasti menahan penutupan. State proses Coucou yang baru dimulai tidak mewarisi countdown sebelumnya. Maksimal 1024 sesi ditahan di memori; bila batas atau ID rusak ditemui, Auto-Quit gagal aman.

Sinyal akhir yang diterima: Codex `SessionEnd` dengan `reason=other` ([source hook Codex](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/hooks/src/events/session_end.rs)); Claude Code `SessionEnd` dengan alasan resmi ([dokumentasi](https://code.claude.com/docs/en/hooks#sessionend)); OpenCode `session.deleted` pada plugin Coucou; Hermes `on_session_finalize` yang diteruskan sebagai `SessionEnd` berpenanda `coucou_lifecycle=finalize` ([dokumentasi observer](https://hermes-agent.nousresearch.com/docs/developer-guide/observer-hooks)). Hermes `on_session_end` adalah batas giliran, sehingga tidak membuka countdown. Penulis relay untuk finalisasi Hermes tidak berstatus daemon agar Python menyelesaikan pengiriman payload pendek sebelum prosesnya keluar; callback tetap tidak menunggu balasan relay/Coucou. [Hooks Antigravity](https://www.antigravity.google/docs/hooks/) tidak memiliki SessionEnd; `fullyIdle` pada Stop tidak menyatakan percakapan ditutup. Antigravity dan Antigravity IDE yang pernah terpantau menahan Auto-Quit sampai Coucou di-Quit manual. Crash, hook akhir yang tidak terkirim, dan sesi lain tanpa sinyal tepercaya juga menahan quit; tidak ada inferensi berdasarkan waktu idle.

Ketika seluruh sesi terpantau berakhir, satu timer 10 menit dimulai. Event kerja baru atau toggle OFF membatalkannya. Saat jatuh tempo, backend meminta konfirmasi island dengan tiket sekali pakai; jawaban frontend tidak hadir/terlambat menahan quit dan pemeriksaan diulang 60 detik kemudian. Settings terlihat, permission tertunda, window Coucou fokus, island expanded/hover, popup respons, Chat/riwayat/draft, upload/drag, dan aktivitas baru menahan quit. Setelah pemeriksaan lolos, backend memanggil `quit_app` yang sama dengan Quit manual. Tidak ada polling agent dan tidak ada Auto-Quit pada peluncuran manual tanpa sesi terpantau.

Aktivasi pada instalasi lokal: jalankan build GUI terbaru satu kali agar `ensure_hook_exe` menyalin relay baru ke `%LOCALAPPDATA%\Coucou\bin`; plugin Hermes **perlu Reinstall** lewat Settings → Agents dengan preview dan backup agar `on_session_finalize` terpasang. Hooks Codex/Claude dan plugin OpenCode tidak perlu Reinstall. Hooks Antigravity tetap seperti sebelumnya. File aktif pengguna tidak ditimpa selama pekerjaan source ini.

Verifikasi source: TypeScript lulus; 227 tes backend Rust, 54 tes relay Rust, 365 tes frontend, dan 5 tes callback plugin Hermes lulus. Satu tes visual Edge dilewati karena sandbox menolak proses browser. Fixture native process lulus; native relay OFF lulus, tetapi skenario ON/named pipe dilewati (`Access denied (5)`) selama Coucou lama masih berjalan. Build Vite terhalang `spawn EPERM`. Pada pemeriksaan terakhir, `target/release/coucou.exe` bertanggal sebelum perubahan Auto-Quit dan binary relay aktif berbeda hash dari release relay terbaru; keduanya belum menjadi bukti pengujian GUI versi baru.

Uji manual Windows: ON Auto-Quit, buka Coucou manual, mulai Codex atau Claude Code lalu berhenti menjawab tanpa keluar—aplikasi harus tetap hidup. Keluar dari sesi; tutup island dan biarkan 10 menit untuk memeriksa proses/tray benar-benar hilang. Ulangi dengan Hermes setelah Reinstall plugin dan OpenCode setelah `session.deleted`; uji dua agent bersamaan, sesi baru sebelum countdown habis, toggle OFF saat countdown, Settings/Chat/permission/popup saat jatuh tempo, lalu jalankan agent lagi untuk memeriksa Auto-Launch. Uji Antigravity dan Antigravity IDE secara terpisah: Stop tidak boleh menutup Coucou. GUI nyata dan countdown fisik 10 menit belum diuji di sandbox.

## Tahap 2C: Antigravity dan Antigravity IDE

Pemeriksaan shortcut Windows menemukan dua executable berbeda: `%LOCALAPPDATA%\Programs\Antigravity\Antigravity.exe` dan `%LOCALAPPDATA%\Programs\Antigravity IDE\Antigravity IDE.exe`. [Dokumentasi Google](https://www.antigravity.google/blog/introducing-google-antigravity-2) juga menyebut Antigravity 2.0 dan Antigravity IDE sebagai aplikasi terpisah. Namun [dokumentasi hooks](https://www.antigravity.google/docs/hooks/) menyatakan keduanya membaca konfigurasi global yang sama, `~/.gemini/config/hooks.json`. Instalasi lokal memuat satu blok `coucou` aktif dengan `PreInvocation`, `PostInvocation`, `PreToolUse`, `PostToolUse`, dan `Stop`, semuanya memanggil relay dengan `--agent antigravity`. File pengguna hanya dibaca; hooks lain tidak diubah. Hooks Coucou yang sudah ada tidak perlu Reinstall bila kedua aplikasi benar-benar memuat blok global ini; periksa daftar hooks dalam masing-masing aplikasi, terutama jika proyek memiliki `.agents/hooks.json` tersendiri.

Kedua aplikasi memakai satu adapter Auto-Launch dan satu pill `agent_antigravity`. Pemicu hanya `PreInvocation`, sebelum pemanggilan model; membuka aplikasi atau workspace saja tidak memicu Coucou. Payload resmi membawa `conversationId` berupa UUID, `invocationNum`, dan `initialNumSteps`; ketiganya divalidasi dan dipakai sebagai kunci deduplikasi tanpa teks prompt, transcript, atau path. Nilai `conversationId` juga dinormalisasi menjadi `session_id` untuk monitoring. `PostInvocation`, tool, dan `Stop` tidak memicu launch. Sesi baru dan lanjutan menggunakan event yang sama, sehingga tidak bergantung pada `SessionStart` yang tidak ada dalam daftar event hooks Antigravity. Semua agent tetap memakai launcher, lock, ledger, toggle, dan startup queue yang sama; Active Pills OFF tidak menahan launch.

Satu pill menampilkan percakapan Antigravity yang terakhir aktif. Ketika dua aplikasi bekerja bersamaan, event tool/Stop dari percakapan yang bukan pemilik pill saat itu diabaikan, dan langkah percakapan sebelumnya dibersihkan saat pill beralih. Respons dari dua sesi tidak digabung. Konsekuensinya, UI tidak menampilkan dua percakapan Antigravity sekaligus. Payload `Stop` resmi tidak menyediakan teks jawaban, sehingga Coucou tidak mengarang isi respons; kartu selesai memakai fallback existing. `PreInvocation` juga dapat dipicu invocation lanjutan atau pekerjaan terjadwal/background; payload yang didokumentasikan tidak memiliki penanda tepercaya untuk membedakannya dari prompt manusia. Karena itu Auto-Launch bisa terjadi pada invocation tersebut setelah pengguna Quit, dan hal ini harus diuji manual.

Relay binary aktif `%LOCALAPPDATA%\Coucou\bin\coucou-hook.exe` berbeda hash dari `target\release\coucou-hook.exe` yang baru dibangun. Binary aktif **perlu diperbarui** dengan membuka build GUI baru satu kali agar `ensure_hook_exe` existing menyalinnya; tidak ada file hooks pengguna yang ditimpa pada tahap ini. Build GUI baru belum tersedia di sandbox karena Vite/esbuild menolak child process (`spawn EPERM`). Jalankan build tanpa installer di terminal Windows lokal yang mengizinkan proses anak: `rtk npm run tauri -- build --no-bundle`, lalu buka `target\release\coucou.exe` sekali sebelum tes Auto-Launch.

Pemeriksaan otomatis: TypeScript lulus; 53 unit relay/launcher dan 211 unit backend lulus; 346 tes frontend lulus, 1 tes visual Edge dilewati karena browser child ditolak sandbox. Fixture native process lulus dan membuktikan child Coucou bertahan setelah relay selesai. Fixture native relay OFF lulus termasuk Antigravity, tetapi skenario pipe/ON dilewati karena `CreateNamedPipeW` mengembalikan `Access denied (5)`; jalankan ulang setelah Coucou Quit di terminal Windows lokal. GUI kedua aplikasi, event payload nyata, dan jumlah tray belum diuji langsung. `cargo fmt --all --check` menunjukkan banyak ketidaksesuaian format yang sudah tersebar di file lain; tidak dilakukan format seluruh repo.

Uji manual terpisah: (1) **Antigravity**: verifikasi Coucou hook aktif pada Settings > Customizations > Hooks, aktifkan Auto-launch, Quit Coucou, buka Antigravity, buka proyek, lalu kirim prompt baru dan prompt lanjutan; Coucou seharusnya terbuka saat invocation model pertama, menampilkan pill Antigravity, dan tidak membuat tray kedua. (2) **Antigravity IDE**: verifikasi hook aktif pada menu agent > Customizations > Hooks, Quit Coucou, buka IDE dan workspace, kirim prompt baru dan lanjutan; periksa hasil yang sama. Uji kedua aplikasi hampir bersamaan, lalu OFF pada toggle untuk memastikan tidak ada launch. Bandingkan session yang tampil dan popup ketika kedua aplikasi bekerja, serta pastikan Coucou tetap hidup setelah selesai. Periksa juga Codex/Hermes/OpenCode/Claude Code pada build baru.

## Tahap 2B: OpenCode dan Claude Code

Launcher, single-instance, lock, ledger 256 event, toggle `autoLaunchWithAgents` (default OFF), cooldown 10 detik, deadline pipe 1,5 detik, dan `CreateProcessW` tetap satu implementasi bersama. `shared/auto_launch_trigger.rs` kini menerima empat agent. Kunci OpenCode/Claude memakai namespace agent sehingga tidak bertabrakan dengan Codex/Hermes. Tidak ada hubungan dengan Windows startup, Active Pills, atau Main Tool. Permission, idle, tool, Stop, SessionEnd dan event tak dikenal tidak memicu launch. Antrean event awal juga mencakup OpenCode dan Claude Code; permission tetap dikirim segera. Tes empat event serentak menemukan startup lock 100 ms dapat kedaluwarsa saat spawn pertama lambat; batas tunggunya dinaikkan ke 800 ms (pembersihan saat pipe sudah tersambung tetap 100 ms), masih di dalam anggaran relay existing. Tes race dengan spawn sengaja ditahan 250 ms kini lulus, sedangkan lock macet tetap keluar dalam kurang dari satu detik.

- OpenCode: template plugin Coucou mendengar `message.updated` dengan `info.role === "user"`, lalu mengirim `UserPromptSubmit` yang hanya berisi `session_id = info.sessionID`, `turn_id = info.id`, dan `cwd`. Ini menangani sesi baru serta prompt berikutnya/sesi lanjutan tanpa mengandalkan `session.created`. Event `session.created`, `session.idle`, `session.deleted`, `session.error`, dan tool existing tetap diteruskan untuk monitoring, tetapi bukan pemicu launch. Plugin tetap fire-and-forget dan tidak mengirim isi prompt ke relay pada pemicu baru. [Daftar event plugin OpenCode](https://opencode.ai/docs/plugins/).
- Claude Code: hook existing tanpa `--agent` tetap dikenali sebagai Claude Code, kecuali sesi Claude Desktop yang memang ditag terpisah. `SessionStart` hanya memicu untuk `source=startup` atau `resume`; `clear`, `compact`, dan `fork` ditolak agar reset dan background fork tidak membuka app. `UserPromptSubmit` menjadi fallback ketika pengguna mengirim prompt berikutnya pada sesi yang tetap hidup. Karena [payload resmi](https://code.claude.com/docs/en/hooks) tidak menyediakan turn ID, relay memakai panjang file transcript pada saat event sebagai cursor per session/event. Isi transcript dan prompt tidak dibaca atau dicatat. Cursor yang sama didedup; perubahan panjang transcript menghasilkan key baru. `PermissionRequest` tetap memakai jalur allow/deny/timeout existing, tanpa menjadi pemicu launch.
- Keterbatasan: dokumentasi Claude menyatakan `UserPromptSubmit` juga dapat muncul dari scheduled task atau laporan subagent background, tanpa field asal yang bisa dibedakan secara andal dalam payload hook. Fallback ini dapat membuka Coucou tanpa ketikan pengguna baru. Cursor ukuran transcript juga dapat menyamakan dua prompt bila file belum bertambah saat kedua hook dipanggil. Verifikasi pada Claude Code nyata tetap diperlukan untuk kasus tersebut; mengganti dengan hash isi prompt akan menambah risiko privasi dan tidak dipakai.

Pemeriksaan read-only mesin ini: plugin aktif Windows berada di `%USERPROFILE%\.config\opencode\plugins\coucou.js` dan masih hanya memakai `session.created`, sehingga **perlu diperbarui** setelah app baru berhasil dibuild. Jangan menimpa plugin aktif langsung: buka build baru sekali, buka Settings → Agents → OpenCode → Reinstall, tinjau preview/diff, lalu Apply; mekanisme existing memeriksa fingerprint, membuat backup bertanggal sebelum menulis, dan menolak file yang bukan buatan Coucou. Restart OpenCode agar plugin baru dimuat. Hooks Claude di `%USERPROFILE%\.claude\settings.json` sudah memuat `SessionStart`, `UserPromptSubmit`, dan `PermissionRequest`, sehingga **tidak perlu diinstal ulang** bila path relay tetap benar. Binary relay aktif `%LOCALAPPDATA%\Coucou\bin\coucou-hook.exe` masih berbeda dari release build baru; buka GUI build baru sekali agar `ensure_hook_exe` menyalin relay baru dan mendaftarkan executable. Source plugin atau relay hasil build saja belum mengubah instalasi aktif. Tidak ada konfigurasi pengguna yang diedit pada tahap ini.

Pemeriksaan tahap ini: TypeScript lulus; 49 unit relay/launcher lulus; 210 unit backend lulus dengan APPDATA/LOCALAPPDATA tes terisolasi, termasuk preview+backup pembaruan plugin; native process lifecycle lulus. Native relay OFF lulus, tetapi skenario named-pipe/ON dilewati karena `CreateNamedPipeW` mendapat `Access denied (5)` pada pipe Coucou yang sedang dipakai/tidak dapat diakses. Tes frontend per file: 343 lulus, 1 tes visual Edge dilewati karena sandbox menolak browser child. `npm run build` berhenti pada esbuild `spawn EPERM`; ini batas sandbox, bukan diagnosis kesalahan source. Build release `coucou-hook.exe` berhasil. `claude --version` melaporkan 2.1.288; `opencode --version` gagal karena executable OpenCode terpasang tidak kompatibel dengan Windows ini. GUI Windows, OpenCode/Claude CLI nyata, tray, dan permission interaktif belum diuji pada build ini.

Uji manual paling singkat di Windows: (1) Quit build lama; di terminal lokal yang mengizinkan subprocess jalankan `rtk npm run tauri -- build --no-bundle`, lalu buka `target\release\coucou.exe` sekali; (2) update plugin OpenCode lewat preview/backup Settings dan restart OpenCode, periksa hooks Claude tetap terpasang; (3) ON lalu Quit Coucou, kirim prompt dari sesi OpenCode baru dan lanjutan, serta Claude Code baru dan lanjutan di terminal Windows dan VS Code; cek satu proses/tray, monitoring, popup jawaban agent non-utama, dan Main Tool tidak berubah; (4) ulangi dua agent hampir bersamaan, lalu OFF untuk memastikan tidak ada launch; (5) uji permission Claude allow/deny/fallback, akhiri seluruh sesi dan pastikan Coucou tetap hidup. Jalankan native relay fixture lagi setelah Quit Coucou nyata: `rtk cargo test -p coucou-hook --test auto_launch_relay --offline -- --nocapture`.

## Catatan Tahap 2A

Implementasi membuka Coucou melalui prompt Codex CLI atau awal sesi/giliran Hermes yang valid. Tahap 1 dan perbaikan monitoring Tahap 1.5 telah lulus pengujian manual Windows oleh pengguna. Tahap 2A menambah adapter Hermes pada launcher bersama; tidak ada Auto-Quit atau dukungan Auto-Launch agent lain.

## Perbaikan Hermes setelah uji manual gagal

Pada Hermes Windows yang terpasang, `agent/conversation_loop.py` melewati `on_session_start` ketika melanjutkan sesi dengan system prompt tersimpan. Plugin Coucou yang aktif hanya mendaftarkan `on_session_start` sebagai pemicu; event tool dan `Stop` tetap diteruskan untuk monitoring tetapi policy peluncuran sengaja menolaknya. Karena itu sesi lanjutan dapat menghasilkan jawaban tanpa satu pun pemicu Auto-Launch. Ini cacat deterministik pada alur tersebut, bukan bukti masalah 9Router. Log lama tidak mencatat nama agent, sehingga belum membuktikan apakah uji manual spesifik pengguna memakai sesi lanjutan; uji GUI ulang tetap diperlukan.

Hermes juga memanggil `pre_llm_call` sekali pada prolog setiap giliran dengan `session_id` dan `turn_id` sebelum API model. Plugin generated yang baru mendaftarkan callback ini dan mengirim payload kanonis `UserPromptSubmit` hanya berisi kedua ID tersebut, tanpa `user_message`. Policy Hermes menerima `SessionStart` atau `UserPromptSubmit` yang lengkap; kedua jenis kunci tetap namespaced dan deduplicated. Codex, `CreateProcessW`, locks, toggle, pipe, permission, dan UI tidak diubah. Bila `SessionStart` terlewat pada sesi lama, event `pre_llm_call` bisa membuka app dan membuat pill Hermes tampil sebagai thinking. `Stop`, tool, permission dan event tak dikenal tetap tidak boleh membuka app.

Plugin aktif `%LOCALAPPDATA%\hermes\plugins\coucou\__init__.py` masih versi lama tanpa `pre_llm_call`; binary `%LOCALAPPDATA%\Coucou\bin\coucou-hook.exe` juga masih hash build sebelumnya, berbeda dari `target\release\coucou-hook.exe` yang baru dibangun. Source saja belum memperbaiki instalasi berjalan. Jangan menimpa plugin aktif tanpa konfirmasi dan backup. Setelah build app baru tanpa installer, gunakan Settings → Agents → Hermes preview/diff lalu Apply (mekanisme existing membuat backup wajib dan menulis atomik), tanpa disable/enable ulang; restart sesi Hermes agar modul Python baru dimuat. Apply existing mencadangkan dan menulis ulang `__init__.py` **serta** `plugin.yaml`, walaupun manifest tidak berubah; periksa dua path backup pada preview. Membuka app build baru sekali memperbarui binary relay lewat `ensure_hook_exe` dan mencatat executable. Jika build app diblokir, jangan memakai Apply dari app lama karena template lamanya masih salah.

## Mekanisme

1. Coucou memakai Tauri 2, backend Rust, frontend TypeScript tanpa framework, dan plugin `tauri-plugin-single-instance` existing. Hook relay adalah binary terpisah `coucou-hook.exe`. Named pipe existing tetap `\\.\pipe\coucou-<SID>`; pemeriksaan pemilik server tetap dipakai.
2. Setelah pemeriksaan single-instance, aplikasi menahan `auto-launch-running.lock` di `%LOCALAPPDATA%\Coucou` selama proses hidup, sebelum membuat tray. Ini juga menutup celah startup ketika mutex plugin sudah ada tetapi window penerimanya belum siap. Lock kedua yang gagal karena sharing violation berhenti sebelum membuat tray; Windows melepas handle ketika proses keluar.
3. Aplikasi mencatat `std::env::current_exe()` yang dikanonisasi ke `auto-launch-executable.json`. Relay menerima hanya path absolut lokal ke file `coucou.exe` yang masih ada. Tidak ada pencarian PATH, shell, registry, maupun path development yang di-hardcode; path dari payload hook tidak digunakan untuk menjalankan program. Saat menguji binary tanpa installer, executable yang dicatat adalah binary uji yang benar-benar dibuka.
4. Relay mencoba pipe existing terlebih dahulu. Policy bersama `shared/auto_launch_trigger.rs` menerima Codex `UserPromptSubmit` dengan `session_id` dan `turn_id`, atau Hermes `SessionStart` dengan `session_id` maupun `UserPromptSubmit` dengan kedua ID; string dibatasi 256 byte. Validasi Codex existing dipertahankan. Hermes harus membawa nama event dan field kanonis dari plugin: alias event, session ID alias, ID kosong/whitespace/control, tipe salah dan agent lain tidak dapat memicu peluncuran. Kunci Hermes dihitung sebelum normalisasi umum, kunci Codex sesudah normalisasi existing. ## Diagnosis lifecycle Windows

Pengujian pengguna menemukan app auto-launch menghilang bersamaan dengan timeout hook 10 detik, sementara app yang dibuka manual tetap hidup. Tidak ada crash event Windows yang cocok. Reproduksi native terisolasi kemudian membuktikan cacat pada spawn awal: `Command::spawn()` dengan ketiga stdio null masih mewariskan handle capture stdout/stderr milik relay. Relay fixture keluar dengan status 0 dalam kurang dari 2 detik, tetapi pembaca kedua pipe tidak menerima EOF selama child hidup. Child juga menjadi anggota Job Object hook; `TerminateJobObject` membunuh child dan baru saat itu EOF diterima. Yang terjadi pada reproduksi adalah terminasi process, bukan UI yang disembunyikan.

Source [runner hooks Codex CLI 0.160.1](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/hooks/src/engine/command_runner.rs) menunggu `wait_with_output()` di bawah timeout hook. Timeout menghentikan process tree melalui Job Object. Source [Job Object Codex](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/utils/pty/src/win/job.rs) mempertahankan descendants jika hook sukses; keluarnya parent secara normal tidak otomatis membunuh app. [Rust Windows CommandExt](https://doc.rust-lang.org/std/os/windows/process/trait.CommandExt.html#tymethod.inherit_handles) menjelaskan default pewarisan seluruh handle inheritable; opsi `inherit_handles(false)` masih unstable pada toolchain yang dipakai. Karena itu helper kecil memakai Win32 API dari dependency `windows` existing. `CREATE_NO_WINDOW` dan deadline startup 1,5 detik tidak diubah.

Tes regresi membandingkan jalur lama dan helper production baru dengan capture pipe serta batas Job Object seperti Codex. Jalur baru memberi EOF untuk kedua pipe dan child tetap hidup lebih dari 10 detik setelah hook sukses dan job dilepas. Path executable pada tes menggunakan spasi, Unicode, dan bentuk canonical Windows; kegagalan spawn file yang tidak ada juga diperiksa. Diagnosis mekanisme ini terbukti secara native, tetapi peristiwa GUI pengguna sebelumnya tidak direkam dengan trace process/handle. Pengguna telah mengonfirmasi Auto-Launch Codex sesudah perbaikan lulus uji manual Windows berulang; hasil GUI Tahap 2A belum diuji.

Log diagnostik lokal `%LOCALAPPDATA%\Coucou\auto-launch.log` dibatasi sekitar 1 MB dan tidak menulis prompt, session/turn IDs, payload hook, maupun API keys. Setiap baris berisi `unix_ms` dan PID:

- `hook_connect agent=... event=... pipe_present=false`, `launch_skipped reason=...`, `trigger_rejected`, `spawned app_pid=... inherit_handles=false`, `pipe_ready` / `pipe_not_ready`, atau `launch_failed` menunjukkan urutan launch dan koneksi tanpa isi payload. Versi log lama belum mempunyai agent/event.
- `hook_exit worker_deadline=... elapsed_ms=...` mencatat penyelesaian relay sebelum process keluar; tidak menambah output protokol stdout/stderr.
- `app_setup auto_launch_arg=...`, `app_duplicate_exit running_lock=true`, `app_exit_requested code=...`, dan `app_exit` menunjukkan startup, penolakan duplikasi, dan keluar melalui lifecycle Tauri. Terminasi eksternal paksa dapat menghilangkan process tanpa marker `app_exit`; tidak adanya marker saja belum membuktikan penyebab terminasi.
